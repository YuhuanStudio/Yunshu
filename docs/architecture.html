Architecture

5-layer stack designed for production inference on Apple Silicon clusters.

5-Layer Stack (L0-L5)

Yunshu follows a strict layered architecture. Each layer only depends on the layer below it. The entire L1-L5 stack is implemented in Python with FastAPI — no Rust, no gRPC cross-language FFI.

L0
Client
Swift app, CLI, SDK — connects via HTTP/WebSocket to L1
SwiftUI app / yunshu_cli (Typer) / yunshu_sdk (Python)
L1
Gateway
FastAPI HTTP server — OpenAI / Anthropic / MCP / Realtime / Admin protocols
python/yunshu_gateway/ — routers: chat, completions, models, embeddings, audio, images, realtime, anthropic, mcp, admin, batch
L2
Control Plane
Scheduling, RBAC, multi-tenant management, model registry
python/yunshu_control/ + python/yunshu_api/ — scheduler, auth, tenant management, model discovery
L3
Compute Mesh
Distributed inference across Apple Silicon nodes via mx.distributed
python/yunshu_mesh/ — JACCL / Ring / MPI topology, node discovery, load balancing
L4
Engine
5-modality inference with continuous batching, speculative decoding
python/yunshu_engine/ — Engine, BatchGenerator, Sampler, SequenceStateMachine, detokenizer, modality handlers (LLM/VLM/TTS/ASR/Image)
L5
KV Hierarchy
4-tier KV cache: Hot (GPU) / Warm (CPU+quantized) / Cool (SSD) / Cold (distributed)
python/yunshu_kv/ — paged attention, KIVI quantization, prefix caching, distributed cache

Key Design Decisions

  • Single-language Python stack (L1-L5) — no Rust, no gRPC cross-language FFI
  • FastAPI for both L1 gateway and L2 management API
  • mlx-lm BatchGenerator as continuous batching engine (not a simple wrapper)
  • Per-request sampler + SequenceStateMachine — Aho-Corasick trie for stop/eos/reasoning state tracking
  • Per-request detokenizer — never pool detokenizers (reset() leaks byte buffers)
  • Single Metal thread — all GPU work via ThreadPoolExecutor(max_workers=1)
  • uv as sole Python package manager (no pip/poetry/pip-tools)

KV Cache Hierarchy

The 4-tier KV cache enables prefix sharing, memory compression, and distributed caching across the compute mesh.

Hot
GPU Resident
  • PagedAttention Metal kernel
  • fp16/bf16 precision
  • Fastest access (<1us)
  • Limited by UMA size
→
Warm
CPU + Quantized
  • KIVI 2-bit/4-bit quantization
  • Metal-accelerated dequant
  • ~8x compression ratio
  • Good for prefix reuse
→
Cool
SSD-backed
  • Disk-backed cache files
  • Prefix sharing across requests
  • Async I/O, non-blocking
  • Large capacity (TB+)
→
Cold
Distributed
  • Across mesh nodes
  • JACCL/Ring transport
  • Multi-node prefix sharing
  • Cluster-scale capacity

Promotion / Demotion

KV blocks are promoted from Cold → Cool → Warm → Hot on access, and demoted in reverse when memory pressure increases. The ProcessMemoryEnforcer monitors GPU memory and triggers eviction when usage exceeds YUNSHU_MAX_MEMORY_GB.

Scheduler Lifecycle

The scheduler manages request queuing, batching, and execution across the 5 modalities.

Client Request | v [L1 Gateway Router] -- parse request, validate params | v [L2 Control Plane] -- auth check, rate limit, model selection | v [Engine Queue] -- per-model request queue | v [Scheduler] -- continuous batching loop | +-- BatchGenerator.insert() -- add to current batch | +-- BatchGenerator.next() -- step generation | | | v | [Response Parser] -- per-request SequenceStateMachine | | +-- Aho-Corasick trie (stop/eos) | v +-- Reasoning state tracking | [Detokenizer] -- per-request detokenizer | | +-- add_token(id) | v +-- last_segment | [Output] -- SSE stream or JSON response | v [Memory Enforcer] -- poll GPU memory, evict idle models [KV Cache] -- store/retrieve KV blocks across tiers

Request Flow Diagram

A typical chat completion request travels through the following path:

HTTP POST /v1/chat/completions | v [Auth Middleware] Bearer token validation (if enabled) | v [CORS Middleware] Origin validation | v [Chat Router] Parse messages, model_id, params | v [Engine Module] Resolve model_id to loaded Engine | v [Engine.generate()] -- or Engine.stream_generate() | +-- Tokenize prompt (tokenizer.encode) +-- Create Sampler (temperature, top_p, seed) +-- Create SequenceStateMachine (stop sequences) +-- BatchGenerator.insert([prompt], max_tokens, [sampler], [ssm]) | v [Generation Loop] ThreadPoolExecutor(max_workers=1) | +-- BatchGenerator.next() -> (prompt_responses, gen_responses) | | | +-- For each response: | +-- SequenceStateMachine.advance(token) | +-- Detokenizer.add_token(token) | +-- Check finish_reason (stop/length/tool_calls) | +-- Yield SSE chunk if streaming | v [Response] | +-- Streaming: SSE chunks + "data: [DONE]" +-- Non-streaming: Full JSON response

Metal Kernel Overview

Custom Metal compute shaders for performance-critical operations on Apple GPU. Located in metal/ directory.

paged_attn
Paged attention kernel for L4 engine. Supports paged KV cache with block tables, eliminating contiguous memory requirements.
Status: Phase 1 (porting)
fa3
Flash Attention 3 for Apple GPU. Memory-efficient attention with tiled computation, reducing peak memory from O(n^2) to O(n).
Status: Phase 2
mla
Multi-head Latent Attention for DeepSeek-style models. Compressed KV projection in Metal.
Status: Phase 3
nsa
Native Sparse Attention kernel. Supports block-sparse attention patterns for long-context models.
Status: Phase 3
sgmv
Segmented Matrix-Vector multiplication for Mixture-of-Experts (MoE) models. Batched expert routing.
Status: Phase 2
kivi_quant
KIVI KV cache quantization kernel. 2-bit and 4-bit quantization/dequantization for warm tier KV compression.
Status: Phase 0 (validation)

Build Pipeline

Metal kernels are compiled with xcrun metal and loaded via MLX's metal framework:

just build-metal    # Compile all .metal files to .metallib
just build          # metal + python + webui (full build)
