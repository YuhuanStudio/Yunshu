title: Console

The console is a small web application served by the Yunshu gateway itself, from the same address and port as the API. It is a view onto one running engine: it shows live status, lets you load and unload models, lists requests, and has a playground for sending test requests. It does not start or stop the Yunshu process and it is not a chat product.

<Callout type="info">
The console interface is written in Traditional Chinese. The labels named below are the ones you will see in it.
</Callout>

## Open the console

Start the server as usual, then open `/console/` on the server's address in a browser. With the default host and port that is port 8000 on `127.0.0.1`, path `/console/`.

The static pages are public so that you can enter a token in the browser. Every API call the console makes still follows the normal authentication rules: when `YUNSHU_AUTH_TOKEN` is set on the server, enter that token in the console (Settings). The token is kept in page memory only and is cleared when you reload or change the server address; it is not stored in the browser, in URLs, in exports or in code snippets.

If `/console/` answers 404 with the text "Yunshu Console is not built", the installed package does not contain the console build. The API is not affected. A source checkout builds the console with Node.js 22.18 or newer and pnpm:

```bash
cd frontend
pnpm install --frozen-lockfile
pnpm build
```

The build is written to `python/yunshu_gateway/console_static`, which the gateway serves.

## Pages

| Page (label in the console) | What it does |
|---|---|
| Overview (`引擎總覽`) | Engine status sampled every three seconds while the page is visible: throughput, request counts, memory and cache figures. You can pause and resume sampling or refresh by hand. |
| Models (`模型庫`) | Lists models with their state; load, unload and warm up models, and manage idle retention. |
| Requests and performance (`請求與效能`) | Live and recently finished requests, filtering, CSV export, request details and per-request cancel. |
| API access (`API 接入`) | Connection snippets for your server and a catalogue of the routes it registers, read from its OpenAPI document. |
| Diagnostics (`引擎診斷`) | Raw data from the server's diagnostic endpoints (system, engine, requests, KV cache, SSD cache, speculative decoding, per-model figures, memory). |
| Playground (`推理測試`) | Streaming chat requests with generation settings. |
| Settings (`設定`) | Server address, access token, theme and per-model idle retention. |

### Overview and requests

The console reads `GET /v1/yunshu/status` every three seconds. If a refresh fails it keeps the last data and marks it as stale or disconnected. History exists only in the page (up to 1,200 observations) and is not stored; reloading the page or seeing the server restart clears it. Values that the server did not report are shown as unavailable, not as zero.

The request list comes from what the status endpoint reports, so it is an observation log, not a complete history. The server provides only the latest finished request, which means that requests that finished between two samples can be missing. Details of an active request are polled from `GET /v1/requests/{request_id}`, and cancelling sends `DELETE /v1/requests/{request_id}`. Finished rows are labelled as ended, not as successful.

### Models

Model operations use `POST /v1/models/load`, `POST /v1/models/unload/{model_id}` and `POST /v1/yunshu/warmup`, with model details from `GET /v1/models/{model_id}`. Unloading asks for confirmation. In single-model mode the model is always kept and cannot be unloaded from the console; the server may also refuse an unload while requests are running. Importing an MLX model from Hugging Face, copying a model under a new name, and deleting use the Ollama-compatible routes `POST /api/pull`, `POST /api/copy` and `DELETE /api/delete`; deleting requires typing the full model id. Import shows that it is waiting on the server, because those routes provide no progress or cancel stream. Per-model idle retention uses the `keep_alive` value of the warmup route.

Model load, unload and delete are operational calls: they need the server's token when `YUNSHU_AUTH_TOKEN` is set, and are refused when no token is configured. See the [models API](/docs/api/models).

### Playground

The playground sends OpenAI-style streaming chat requests and shows content and reasoning output. You can set thinking mode (auto, on, off), the output format (text or JSON), temperature and other generation settings. For vision-language models you can attach a PNG, JPEG or WebP image of up to 8 MB; it is sent as an OpenAI image part and never stored. Stopping, or leaving the page, aborts the stream. A reply cut off by the length limit is marked as such, and partial or failed assistant messages are not sent back as context in later turns. Speech, video generation and tool execution are not mapped onto chat in the playground; use the API for those.

### Diagnostics

The diagnostics page reads the server's authenticated diagnostic endpoints. A diagnostic that is disabled or missing on your server is reported as such. API discovery reads `/openapi.json` from the server you are connected to rather than a built-in route list.

## Connection settings

By default the console talks to the same origin that served it. In Settings you can point it at another Yunshu server; that server must then allow the console's origin through its CORS configuration (`YUNSHU_CORS_ORIGINS`). Only the server address and the theme are saved in the browser's local storage. If authentication fails, polling pauses until you retry or change the connection.

## What the console does not do

- It has no API key management and no usage quotas. Access control is the single `YUNSHU_AUTH_TOKEN` described in [Configuration](/docs/guides/configuration).
- It does not change the server's startup configuration or disable authentication.
- It keeps no durable request history.
