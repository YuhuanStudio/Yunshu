description: 如何用 token 或逐密钥配额保护 Yunshu 服务器、从 API 写入设置、编辑 CORS 来源，以及内置防护的作用。
---

Yunshu 是单节点、单一操作者的服务器。访问控制分为三层，全部在本机：静态 token、附配额的可选 API 密钥，以及 CORS 来源。

## 静态 token

设置 `YUNSHU_AUTH_TOKEN`（或以 `--auth-token` 启动）。之后除了 health、version 与文档之外，每个请求都需要 `Authorization: Bearer <token>` 或 `x-api-key`。文本 WebSocket 端点也接受 `?token=`。

| 状态 | 推理路由 | 运维路由（加载／卸载模型、设置、密钥、日志、诊断） |
|---|---|---|
| 已设置 token | 需要 token | 需要 token |
| 没有 token 且没有保存的 API 密钥 | 开放 | 拒绝 |
| `YUNSHU_AUTH_DISABLED=1` | 开放 | 开放 |

<Callout type="warn">
token 是管理员凭证。`YUNSHU_AUTH_DISABLED=1` 会开放一切，只适用于本机开发。`YUNSHU_HOST` 默认为 `127.0.0.1`；绑定 `0.0.0.0` 之前请先设置 token。
</Callout>

## 附配额的 API 密钥

除了静态 token，操作者可以创建多把密钥。每把密钥有范围（`infer`、`admin`）、可选的到期时间，以及配额（`requests_per_day`、`tokens_per_day`、`max_concurrent`）。可在主控台的 Keys 页面管理，或使用具 admin 范围的 API。

<Steps>
<Step>

创建密钥。`secret` 只会在响应中出现一次；`~/.yunshu/keys.json`（权限 0600）中只保存哈希。

```bash
curl -s -X POST localhost:8000/v1/yunshu/keys \
  -H "Authorization: Bearer $YUNSHU_AUTH_TOKEN" \
  -H 'content-type: application/json' \
  -d '{"name":"laptop","scopes":["infer"],"quotas":{"requests_per_day":1000,"max_concurrent":2}}'
```

</Step>
<Step>

把 secret 交给客户端，作为它的 API 密钥。

</Step>
<Step>

查看每把密钥的每日用量（请求、提示词、完成与缓存 token、错误）：

```bash
curl -s localhost:8000/v1/yunshu/usage -H "Authorization: Bearer $YUNSHU_AUTH_TOKEN"
```

</Step>
</Steps>

对密钥使用 `PATCH` 与 `DELETE` 可编辑与移除，`POST /v1/yunshu/keys/{id}/rotate` 会重新签发。超过配额时，会以该路由自己的错误格式返回 `429` 并附 `Retry-After`。这些路由列于 [Yunshu 扩展](/docs/api/extensions)与[运维](/docs/api/operations)。

密钥不是租户。通过验证的客户端共用 Files、已保存的 completions 与 Evals 数据，没有逐密钥隔离，也没有 RBAC。Realtime WebSocket 接受密钥，但不计算配额。

## 写入设置

`GET /v1/yunshu/config` 会列出每个设置的值、默认值、来源，以及变更何时生效（`live`、`reload` 或 `restart`）。`PATCH /v1/yunshu/config` 会验证并以原子方式保存变更（全部成功或全部不变，文件权限 0600）。环境变量或 CLI 的值仍然优先，并标示为 `overridden`。`dry_run` 可预览变更。

需要重新启动的设置会被标记，让主控台提示你。只有在服务器由 launchd 运行时，`POST /v1/yunshu/service/restart` 才会重新启动服务器。主控台的设置页面提供相同功能，并有搜索框与逐项控制。所有设置请见[设置](/docs/guides/configuration)。

## CORS

`GET` 与 `PATCH /v1/yunshu/cors`，以及主控台设置页面，都可即时编辑允许的来源。`YUNSHU_CORS_ORIGINS` 默认为 `http://localhost:3000,http://localhost:8000`。

- 来源格式为 `scheme://host[:port]`，最多 50 个。
- 通配符（`*`）需要明确确认，不能与其他来源并用，且会停用 credentials。会发送 cookie 或 authorization 标头的浏览器必须使用明确的来源。
- 同一份清单也用来检查 Realtime 与文本 WebSocket 的 `Origin` 标头。
- 绑定地址与局域网暴露在此 API 中为唯读。

## Host 与 Origin 检查

绑定在 loopback 地址的服务器会检查 `Host` 头，网页因此无法经 DNS rebinding 连到它。接受 `localhost`（含 `localhost.` 与 `*.localhost`）、任何 `127.0.0.0/8` 写法（`127.0.0.1`、`127.1`）、`[::1]` 与未指定地址（`0.0.0.0`、`[::]`），任意端口。其他一律返回 `403`，消息会指出该头的值与对应设置。绑定 `0.0.0.0` 的服务器在未设置 `YUNSHU_ALLOWED_HOSTS` 时不做检查。

- 反向代理、`tailscale serve`、cloudflared 隧道或 `ssh -L` 若把对外名称作为 `Host` 转给 loopback 服务器，必须把该名称加入 `YUNSHU_ALLOWED_HOSTS`（逗号分隔；`*` 关闭检查）。
- loopback 绑定不接受 `host.docker.internal`：容器要连到主机 loopback，服务器必须监听 loopback 以外（`YUNSHU_HOST=0.0.0.0`），此时检查本来就关闭。
- 带有 `Origin` 且不带凭证的状态变更请求，必须来自 loopback、请求自身的 origin 或 `YUNSHU_CORS_ORIGINS`。自定义协议请列 `scheme://*`（例如 `vscode-webview://*`）或完整 origin（`app://.`）。`Origin: null` 一律拒绝。带 `Authorization` 或 `x-api-key` 的请求不受影响。

## 登录失败

非 loopback 的客户端地址在 60 秒内提交 20 次错误凭证后，后续错误凭证会得到 `429` 与 `Retry-After`。正确的 token 或密钥一律通过并清除该客户端的计数；完全没有凭证的请求返回 `401`，不计数。`YUNSHU_TRUSTED_PROXIES` 列出连接的代理时，以 `X-Forwarded-For` 的最后一项为客户端地址，否则使用连接对端地址。

## 其他防护

- 模型下载重定向到其他来源时，会丢弃 Authorization、API 密钥与 cookie 标头。
- Realtime 临时 secret（`ek_...`）与日志行中的凭证会被屏蔽。转录用的 secret 无法创建模型响应。
- `web_fetch` 会拦截私有、loopback 与 link-local 地址（包含重定向之后），除非设置 `YUNSHU_WEB_FETCH_ALLOW_PRIVATE=1`。含路径穿越的仓库 ID 会在访问磁盘前被拒绝。
- `YUNSHU_RATE_LIMIT_RPM`（默认 `0`，关闭）限制每个客户端每分钟的请求数；当服务器暴露给其他机器时请设置。
- 不会发送任何使用分析数据。本机会采样什么，请见[主机遥测](/docs/guides/telemetry)。
