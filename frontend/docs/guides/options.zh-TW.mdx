---

Yunshu 的規則很單純：**無損**最佳化（與一般路徑產生相同的 token）可以成為預設值；**有損或輸出不相同**的最佳化則是穩定的使用者選項，預設關閉，不會因為某次基準測試就替你打開。本頁列出所有這類選項。預設值定義在設定註冊表（`python/yunshu_engine/settings.py`），實際生效的值可用 `yunshu config` 查看。完整設定表請見[設定](/docs/guides/configuration)。

<Callout type="warn">
第一節的四個選項（`YUNSHU_SPEC_UNVERIFIED`、`YUNSHU_DRAFT_MODEL`、`YUNSHU_ENGINE_LOOP`、`YUNSHU_OVERLAP`）是穩定選項，不是實驗功能，但**不保證產生與預設路徑相同的 token**。只有在你接受輸出可能與一般解碼不同時才開啟。每個選項的限制見下文。
</Callout>

## 輸出不相同的服務選項

這四個選項都只適用於純文字的 `mlx-lm` 模型。Qwen3.5 系列的 VLM runner 有自己的無損推測解碼（MTP、DFlash），不使用它們。請見[推測解碼](/docs/internals/speculative-decoding)。

| 設定 | 預設值 | 作用 |
|---|---|---|
| `YUNSHU_SPEC_UNVERIFIED` | `''`（關閉）或 `eagle` | 在文字模型上啟用以外部 `mlx-lm` draft 模型進行的推測解碼 |
| `YUNSHU_DRAFT_MODEL` | 未設定 | `YUNSHU_SPEC_UNVERIFIED=eagle` 使用的 draft 檢查點路徑 |
| `YUNSHU_ENGINE_LOOP` | 關閉 | 文字模型改用連續批次迴圈，而不是單一請求的快速路徑 |
| `YUNSHU_OVERLAP` | `''`（關閉）、`cpu_gpu` 或 `two_batch` | 讓該迴圈中的 CPU 與 GPU 工作重疊 |

### 外部 draft 模型（`YUNSHU_SPEC_UNVERIFIED` 與 `YUNSHU_DRAFT_MODEL`）

`YUNSHU_SPEC_UNVERIFIED=eagle` 會載入由 `YUNSHU_DRAFT_MODEL` 指定的另一個較小的 `mlx-lm` 檢查點（`python/yunshu_engine/batched_engine.py` 的 `_init_external_lm_spec`），並用它產生草稿。若未設定 `YUNSHU_DRAFT_MODEL`，引擎會在模型設定中找 `draft_model_path`；兩者都沒有時就什麼都不載入，開關未設定時絕不會載入第二個模型。

- `eagle` 是歷史遺留的路由名稱。一般語言模型就能當 draft，不需要訓練過的 EAGLE head。
- 只有貪婪（temperature 為 0 或未設定）、非串流、要求推測或預設啟用推測、且使用預設取樣與懲罰參數的請求才會走這條路。Schema 或文法限制、自訂 logits processor、stop 字串、思考預算、LoRA 與 token mask 選項仍走一般快速路徑，logprobs 請求也是。
- 輸出不保證與一般解碼逐 token 相同。註冊表記錄 2026-10-24 的一次檢查中，試過的每個提示都出現差異，速度則依提示從變慢到變快不等；這些數字不在基準測試紀錄中，因此這裡不引用。
- 當你有一個與大型文字模型相配的小型 draft，且重視速度勝過精確重現時才使用。要無損推測請用 n-gram 或 suffix 草稿（`YUNSHU_NGRAM_DEFAULT`、`YUNSHU_SPEC_PROPOSER`）或 Qwen3.5 系列 runner。

### 連續批次迴圈（`YUNSHU_ENGINE_LOOP`）

設定 `YUNSHU_ENGINE_LOOP=1` 後，文字模型改由 `EngineCore`（`python/yunshu_engine/engine_core.py`）服務，它會把並行請求合批；否則由 `_generate_fast` 服務，並行請求會被序列化。

- 多個並行文字請求時，總吞吐量較高；只有一個請求時，註冊表記錄有小幅損失。確切數字不在基準測試紀錄中，因此這裡不列出。
- 批次輸出與單一請求路徑不保證逐 token 相同，因為批次的數值計算不同。
- 部分功能在迴圈上行為不同，例如 SpecPrefill 不會套用。
- 它不影響 VLM，VLM 一律使用 VLM batch runner。

適合並行用戶端很多、吞吐量比逐位元可重現性更重要的純文字伺服器。

### CPU 與 GPU 重疊（`YUNSHU_OVERLAP`）

`cpu_gpu` 讓排程工作與 GPU 步驟重疊；`two_batch` 把一個批次切成兩半讓它們重疊。兩者都在 `EngineCore` 啟動時讀取，因此只有搭配 `YUNSHU_ENGINE_LOOP=1` 才有意義，並繼承其輸出不相同的特性。註冊表記錄在 3B 文字模型上沒有可量測的效果（2026-10-24），除非你在自己的模型上量到好處，否則請保持關閉。

## 有損記憶體選項

這些選項以品質換取記憶體或磁碟。全部預設關閉（預設值是無損值）。有損選項不會因為基準測試而變成預設值。

| 設定 | 無損預設值 | 有損值 | 作用 |
|---|---|---|---|
| `YUNSHU_KV_PRECISION` | `bf16` | `int8` | Qwen3.5 系列共用解碼批次使用 int8 KV；記憶體與頻寬較少，注意力有小誤差。單一請求與推測 lane 維持 bf16 |
| `YUNSHU_KV_QUANT_BITS` | `off` | `auto`、`2`、`3`、`4`、`8` | 文字引擎的量化 KV 快取 |
| `YUNSHU_PREFIX_HOT_LIMIT` | `0`（全部完整精度） | 一個數量 | 只讓該數量的前綴 KV 項目維持完整精度，較舊的以 4-bit 存放在 RAM；重用時有損 |
| `YUNSHU_SSD_CACHE_PRECISION` | `native` | `int8` | 文字 SSD 前綴快取以逐 tensor int8 儲存；重用時有損 |
| `YUNSHU_VLM_APC_WARM` | `off` | `int8`、`int4` | 壓縮的 WARM 前綴層；命中時還原的是反量化的 K/V，輸出可能與冷 prefill 不同。`lossless` 則是精確的 |
| `YUNSHU_QUANT_MODE` | `''`（沿用檢查點） | `mxfp4`、`nvfp4`、`mxfp8`、`affine` | 載入時在記憶體中量化權重 |

`YUNSHU_QUANT_CONFIG` 設定 `affine` 的位元數與群組大小。記憶體管理請見[記憶體管理](/docs/internals/memory)。

## 規則

| 類型 | 例子 | 可以成為預設值嗎？ |
|---|---|---|
| 無損（輸出相同） | 佈局、kernel、排程器、batch-invariant 推測、無損快取壓縮 | 可以，需先通過 A/B 與一致性檢查；可保留關閉選項 |
| 有損或輸出不相同 | 本頁所有選項 | 不可以。作為穩定選項，預設為無損值 |

要確認某個選項是否改變你的輸出，請用相同提示在開啟與關閉下各做一次貪婪解碼並比對 token；一致性工具請見[驗證](/docs/developers/verification)。
