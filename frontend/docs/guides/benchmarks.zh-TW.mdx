`gaps_full_1109`（2026-11-09；私有研究筆記，不在本倉庫中），該研究由原始列資料產生。競爭對手：TensorFold 1.1.8 與 1.2.1、
Splash 1.5.0、llama.cpp b12061、oMLX 0.7.3 與 0.7.3rc1、mlx-lm-server 0.32.2、mlx-vlm-server 0.7.11 與 mlx-serve 26.11.1。
Kapitsa 0.2.26 與 LM Studio 已排除（見下文）。

2026-10-19 的 27B 快照已被本次執行取代，此處不再重複。它作為帶日期的報告保留：[RELEASE_016 快照 2026-10-19](https://github.com/YuhuanStudio/Yunshu/blob/main/docs/reports/RELEASE_016_BENCHMARKS_2026-10-19.md)。

## 如何閱讀這些數字

- 每個數值是 2 或 3 次重複的中位數。許多雲樞單元格另外進行了一次未計畫的第三次重複。
- 研究有兩種口徑。STRICT 只有在雙方都通過每項審計檢查時才計入一列，因此只剩 18 個可比列，全部來自批次 B1。REF 還忽略兩項記帳性失敗：B2 中混用了兩個 harness 提交，以及一個未計畫的額外重複檔案。下列每個數字都是 REF 數字。在 REF 下，每個數字所用的雲樞一側只帶有 REF 豁免的檢查，重啟列除外（見其他單元格）。
- 已排除：所有 Kapitsa 單元格（啟動的二進位雜湊與固定的不一致，因此不使用其 RAW 勝出結果）；tool-chat 解碼 tok/s（27 token 的回覆使計時視窗過短；tool-chat TTFT 保留）；128K 混合負載的逐列中位數（角色不同；採用彙總值）；重啟解碼 tok/s（不同引擎之間不可比）；LM Studio（從未執行）。
- 百分比遵循研究口徑。正值表示雲樞更好。百分比取雲樞 main 與雲樞 pb2 中較好的一個，而顯示的雲樞數值為 main 欄（與 README 中數值相同）。當 pb2 更快時，顯示的比值可能與百分比不同。
- 範圍：32K、64K 與 128K 的程式碼和散文提示詞，以及下文列出的並行、混合與重啟單元格。該研究不能確立一般品質或一般排名。

## 雲樞的定位

在完整矩陣中，REF 共有 114 個可比列。雲樞贏 17 列，輸 97 列：輸給 Splash（37）、TensorFold 1.1.8（36）、TensorFold 1.2.1（22）、llama.cpp（1）與 mlx-serve（1）。其中四十個失敗出現在 32K 及以上。

在程式碼提示詞上，TensorFold 在每個深度都領先 27B 解碼；在散文上，TensorFold 在 32K 與 64K 領先，Splash 在 128K 散文解碼領先。冷 TTFT 在 32K 與 64K 落後於 Splash，在 128K 領先。溫 TTFT 在 32K 領先，在 64K 與 128K 落後。後續輪（turn-2）TTFT 在每個深度都落敗，其中最大差距出現在 64K（程式碼 -61.5%）。

### 其他單元格

- 不同的 8K 提示詞，彙總解碼 tok/s，程式碼。雲樞 main（pb2）在 2、4 與 8 個並行請求下：
  27.3（36.8）、33.0（38.5）與 37.1（39.1）。最佳競爭對手（REF）：TensorFold 1.2.1 42.3、TensorFold 1.2.1 45.1、
  TensorFold 1.1.8 45.2。雲樞相對最佳：-13.1%、-14.7% 與 -13.5%。Kapitsa 已排除。
- 混合 128K，程式碼，8 個並行（一個 128K 長請求和 7 個短請求）。彙總 tok/s：16.1（pb2 18.1），對比 Splash 17.7，+2.0%。長請求 TTFT：222.256 s（pb2 212.084 s），對比 Splash 224.558 s，+5.9%。逐列中位數不是同口徑比較，因此不予報告。
- 近似相同快取下的 turn-2（研究中的 idle5 單元格，程式碼，32K）：TTFT 0.983 s，已快取 32704 個 token；對比 TensorFold 1.1.8 的 0.070 s，已快取 33283 個 token，-92.9%。64K 與 128K 的 turn-2 在程式碼和散文上落後 31% 至 61%。
- 程式碼 turn-2 解碼，32K：342.2 tok/s（pb2 347.0），對比 Splash 127.2，+168.9%。研究未解釋這一結果，因此不將其視為普遍結論。
- 重啟，程式碼，32K：重啟 TTFT 32.868 s，對比 mlx-serve 26.11.1 的 0.313 s，-99.0%。兩個雲樞引擎在重啟後都顯示 0 個已快取 token（審計項 `cold_cache` 失敗），因此磁碟層還原未被證明。該重啟項已重新開啟。
- 結構化輸出（json-schema，8K，冷解碼）：74.3 tok/s（pb2 24.0，未通過 engaged 模式），對比 TensorFold 1.1.8 的 163.8，-54.6%。
- Flash-Next（Qwen4）不在本次比較之中。

### 研究遺留的待辦事項

- Kapitsa 必須重新固定版本（其二進位雜湊已變化），其單元格才能計入。
- 有 50 個單元格帶有未計畫的 r2 檔案，需要做出決定，然後重新審計。
- 為整個批次固定同一個 harness 提交（B2 混用了兩個）。
- 重新執行 B1 中 pb2 在 32K 與 64K turn-2 的輪次時間異常值。
- 執行 LM Studio，或將其從清單中移除。
- 在真實解碼視窗上測量 tool-chat 解碼（27 token 的回覆使目前 tok/s 失去意義）。
