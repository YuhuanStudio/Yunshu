description: Yunshu 提供的 HTTP、SSE、WebSocket、Realtime、WebRTC 与 Unix socket 传输方式、多路复用文本 WebSocket 协议，以及未提供的内容。
---

Yunshu 以多种传输方式提供同一个应用程序。每一种都分发到相同的处理器，所以验证、中间件、请求 id、前缀缓存与取消的行为完全一致。

| 传输方式 | 端点 | 状态 |
|---|---|---|
| HTTP 与 SSE | `POST /v1/chat/completions`、`/v1/responses`、`/v1/messages` | 稳定 |
| 文本 WebSocket（多路复用） | `WS /v1/stream` | 稳定，Yunshu 协议（见下） |
| Responses WebSocket 模式 | `WS /v1/responses` | 稳定，OpenAI 的协议 |
| Realtime WebSocket | `WS /v1/realtime`（GA schema；加上 `OpenAI-Beta: realtime=v1` 为 beta）与 `/realtime`（beta） | 稳定 |
| Realtime WebRTC | `POST /v1/realtime/calls` | 可选 `yunshu[webrtc]` |
| Unix domain socket | `yunshu serve --uds PATH` | 稳定 |
| HTTP/2（h2c） | 未提供 | 无 |

## 规范怎么说

**Responses WebSocket 模式。** 依 OpenAI 的 WebSocket 模式指南，客户端以 WebSocket 连到 `/v1/responses`（SDK：`client.responses.connect()`），发送 `{"type":"response.create", "model", "input", "store", "previous_response_id", "generate", "stream_id"}`，并收到与 SSE 流式输出相同、原样的 `response.*` 事件，外加 `error`。相同 `stream_id` 的请求按顺序运行、绝不重叠；不同 id 则并行。继续对话使用 `previous_response_id`，只带新的输入项。Yunshu 在 `WS /v1/responses` 实现了这个模式。

**Anthropic Messages。** SSE（`stream: true`）是唯一的官方流式传输方式；没有 WebSocket 模式可以对齐。Messages 可通过 Yunshu 自己的 `/v1/stream`（`api: "messages"`）使用。

**OpenAI Realtime。** WebSocket 位于 `/v1/realtime?model=M`，使用 `Authorization: Bearer`（浏览器使用子协议 `realtime` 与 `openai-insecure-api-key.<key>`），为 JSON 文本帧。GA session 有 `type: "realtime"`、`output_modalities`、`audio.input` 与 `audio.output`、`instructions`、`tools` 与 `tool_choice`。音频格式为 `audio/pcm`（24 kHz、单声道、16 位）、`audio/pcmu` 与 `audio/pcma`；回合检测为 `server_vad`、`semantic_vad` 或 null。WebRTC 则是把 SDP offer 发送到 `/v1/realtime/calls`，并在 `oai-events` 数据通道上交换相同的事件。

## 文本 WebSocket：WS /v1/stream

这是 Yunshu 协议，用于没有官方 WebSocket 模式的情况（chat completions、completions、messages）以及多路复用的额外功能。一条连接可同时承载许多并行请求。服务器事件与 SSE 流式输出以 `data:` 载荷携带的对象相同，并以客户端的请求 id 包装。

<Steps>
<Step>

以与 HTTP 相同的方式验证连接（`Authorization: Bearer`、`x-api-key` 或 `?token=`）。Origin 与凭证会在升级之前检查，所以被拒绝的客户端会得到 HTTP 403 的握手失败。

</Step>
<Step>

读取服务器的第一则消息 `session.created`。其中列出 `apis` 与 `limits`（`max_inflight`、`max_stream_ids`、`send_queue`、`ping_interval_s`）。

</Step>
<Step>

发送请求帧。`body` 就是普通的 HTTP 请求体；`stream` 会被强制开启，对 chat 与 completions，`stream_options.include_usage` 默认为 true。

```json
{"type": "request", "id": "a", "api": "chat.completions", "body": {"model": "local", "messages": [{"role": "user", "content": "Hi"}]}}
```

</Step>
<Step>

读取 `event` 帧，直到该 id 的终止 `done` 帧为止。

</Step>
</Steps>

客户端到服务器（JSON 文本帧）：

| 消息 | 意义 |
|---|---|
| `{"type":"request","id":"a","api":"chat.completions\|completions\|responses\|messages","body":{...},"stream_id":"s"}` | 开始请求（`stream_id` 为可选） |
| `{"type":"cancel","id":"a"}` | 中止；生成停止（与 SSE 客户端断线相同的路径）；以 `done(cancelled)` 结束 |
| `{"type":"stop","id":"a"}` | 按需停止；以 `done(stopped)` 结束 |
| `{"type":"update","id":"a","max_tokens":N}` | 将流式 delta 总数（约每个 token 一个）限制为 N；以 `done(max_tokens)` 结束 |
| `{"type":"ping","t":..}` 与 `{"type":"pong"}` | 双向存活检查 |

服务器到客户端：

| 消息 | 意义 |
|---|---|
| `{"type":"session.created","protocol":"yunshu.stream","apis":[...],"limits":{...}}` | 第一则消息 |
| `{"type":"event","id":"a","event":"<SSE event name or null>","data":{...}}` | 一个 SSE 事件。chat 的 `data` 是 `chat.completion.chunk`；responses 与 messages 则是具名事件 |
| `{"type":"done","id":"a","reason":"completed\|cancelled\|stopped\|max_tokens\|error","stats":{"ttft_ms","duration_ms","events","deltas"}}` | 每个请求的终止消息；同时带有 `request_id` |
| `{"type":"error","id"?,"status":404,"error":{...}}` | 请求层级（带 `id`）或连接层级的错误；上游 HTTP 错误保留其状态与响应体 |
| `{"type":"ping","t":...}` | 每 `YUNSHU_WS_PING_INTERVAL` 秒一次的心跳 |
| `{"type":"updated","id","max_tokens"}` | `update` 的确认 |
| `{"type":"progress","id",...}` | 排队与预填进度：SSE `: yunshu-progress` 注释的字段（`phase`、`percent`、`processed_tokens`、`tokens_per_second`、`eta_s`、`queue_position` 等） |
| `{"type":"stats","id",...}` | 每个响应的统计：`x_yunshu` 对象的字段（`ttft_ms`、`decode_tps`、缓存命中等）。请见 [Yunshu 扩展](/docs/api/extensions) |

### 规则

- `id` 是客户端的请求 id。当它适合用作标头（1 到 128 个 `A-Za-z0-9._:-` 字符）时，它同时也是 HTTP 的 `X-Request-Id`，因此 `GET` 与 `DELETE /v1/requests/{id}`、日志与错误提示都使用同一个 id。否则由处理器生成一个，并以 `request_id` 在 `done` 中报告。
- 每条连接最多同时运行 `YUNSHU_WS_MAX_INFLIGHT`（默认 16）个请求；超过会得到 `429 too_many_requests`。重复使用进行中的 id 是 `409`。共用 `stream_id` 的请求按顺序运行；每条连接最多 32 个 stream id。
- 背压：每条连接的输出队列有上限（`YUNSHU_WS_SEND_QUEUE`，默认 256 个事件），所以慢速的读取端会阻塞应用程序的 `send()`，生成会暂停而不是缓冲。心跳绝不会排在停滞的读取端后面。
- 关闭 socket 会取消所有进行中的请求。

| 设置 | 默认 | 作用 |
|---|---|---|
| `YUNSHU_WS_MAX_INFLIGHT` | `16` | 每条连接的并行请求数 |
| `YUNSHU_WS_PING_INTERVAL` | `15.0` | 心跳间隔（秒）；`0` 为停用 |
| `YUNSHU_WS_SEND_QUEUE` | `256` | 生成暂停前缓冲的输出事件数 |

### Responses WebSocket 模式

`WS /v1/responses` 使用 OpenAI 的协议：发送 `{"type":"response.create", ...body..., "stream_id"?}`，并接收原样的 `response.*` 事件。`stream_id` 通道的运作如上。Yunshu 另外加入 `{"type":"response.cancel","stream_id"|"id"}`。此方言不会发送 progress 与 stats 事件，因为 OpenAI 的协议没有位置放它们。官方 `openai` SDK（`client.responses.connect()`）是参考客户端。

### Python 客户端

```python
from yunshu_client import YunshuStream

async with YunshuStream("ws://127.0.0.1:8000/v1/stream", token=None) as conn:
    async for m in conn.chat({"model": "m", "messages": [...]}, id="a", with_done=True):
        ...                      # events, then the done message
    await conn.cancel("a")       # from any task
```

`examples/ws_stream.py` 在同一条 socket 上流式传输两个聊天并取消其中一个。

## Realtime

`/v1/realtime` 以握手时选定的两种方言实现 OpenAI Realtime 协议：GA（默认，也是 `client.realtime.connect()` 使用的）与 beta（`OpenAI-Beta: realtime=v1`，以及旧式的 `/realtime` 路径）。session 引擎是共用的；`yunshu_gateway/realtime_ga.py` 在 socket 边界转换事件名称与 session 形状。验证与 Origin 会在升级之前检查（HTTP 403）。请见 [Realtime API 参考](/docs/api/realtime)。

与 api.openai.com 的差异：

- `semantic_vad` 以 `server_vad` 提供；`eagerness` 会被忽略。
- `turn_detection.idle_timeout_ms`：完成一次响应后（再加上其音频的播放时间），在这段时间内用户没有说话，服务器会发送 `input_audio_buffer.timeout_triggered`，把空缓冲区当作一次无声的用户回合提交并响应。
- `audio.input.noise_reduction`（`near_field` 或 `far_field`）会在 VAD 与 ASR 之前应用因果式 CPU 高通滤波与噪声底限扩展器。这是轻量滤波，不是神经网络降噪。
- `rate_limits.updated` 跟在 `response.created` 之后。本机服务器没有配额：`requests` 报告 `YUNSHU_RATE_LIMIT_RPM`（为 0 时是 2^31-1，代表无限制），`tokens` 报告模型的 context window。
- `output_audio_buffer.started`、`.stopped` 与 `.cleared`（仅 GA 方言）标示一次响应音频的范围；客户端事件 `output_audio_buffer.clear` 会取消正在说话的响应。
- `response.create.input` 会取代该次响应的对话上下文；搭配 `conversation: "none"` 可让它不进入历史。
- 不支持的 session 字段会被静默透传，不会生成 `invalid_request_error`。

### WebRTC

<Steps>
<Step>

安装 extra：`uv pip install 'yunshu[webrtc]'`。没有它时，`POST /v1/realtime/calls` 会返回 503，可改用 `WS /v1/realtime`。

</Step>
<Step>

将 SDP offer 发送到 `/v1/realtime/calls`（`application/sdp`，或 multipart 的 `sdp` 加上 JSON `session`），与 `client.realtime.calls.create` 相同。服务器返回 201、一份 SDP answer 与 `Location` 通话 ID。

</Step>
<Step>

在 `oai-events` 数据通道上交换事件，它与 GA Realtime session 共用。音频走 RTP 轨道。

</Step>
</Steps>

输入音频会在 CPU 上重采样为 24 kHz 单声道 PCM16，输出 PCM 使用有上限的两秒缓冲。session 会在对端失败、客户端通道关闭、服务器关闭或一小时后结束；没有打开通道的 offer 在 60 秒后过期；同时最多保持 16 通通话。临时 client secret 也可用于验证此端点。没有公共的 STUN 或 TURN 服务器，所以 loopback 与局域网的对端需要可直连的 ICE 候选。不提供 SIP 通话管理与监控用的旁路 WebSocket。

## Unix domain socket

`yunshu serve --uds /path/y.sock`（设置 `YUNSHU_UDS`）会在 socket 上提供相同的应用程序，而不是 TCP。`--host` 与 `--port` 会被忽略，残留的 socket 文件会被移除。以文件所有者专属的权限作为访问控制，因此这是最安全的本机传输方式：没有端口，也没有网络暴露。

<Tabs items={["curl", "Python"]}>
<Tab value="curl">

```bash
curl --unix-socket /path/y.sock http://localhost/v1/models
```

</Tab>
<Tab value="Python">

```python
import httpx, openai

client = openai.OpenAI(
    base_url="http://yunshu/v1",
    api_key="x",
    http_client=httpx.Client(transport=httpx.HTTPTransport(uds="/path/y.sock")),
)
```

</Tab>
</Tabs>

`YunshuStream(url, uds=path)` 对 WebSocket 同样适用。OpenAI SDK 自己的 Realtime 与 Responses WebSocket 客户端会打开 TCP 连接，所以它们请使用 TCP 端口。

## HTTP/2

未提供。uvicorn 只支持 HTTP/1.1，而 h2c 需要第二套服务器堆栈（hypercorn 或 granian），各有自己的 lifespan、WebSocket 与断线语义。以断线驱动的取消与多路复用 WebSocket，已覆盖 HTTP/2 本来能带来的好处：单一连接上的多个并行的流，且请求之间没有 head-of-line 阻塞。
