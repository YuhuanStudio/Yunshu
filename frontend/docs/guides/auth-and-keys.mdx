---

Yunshu is a single-node, single-operator server. Access control has three layers, all local: a static token, optional API keys with quotas, and CORS origins.

## Static token

Set `YUNSHU_AUTH_TOKEN` (or start with `--auth-token`). Then every request except health, version and docs needs `Authorization: Bearer <token>` or `x-api-key`. The text WebSocket endpoints also accept `?token=`.

| State | Inference routes | Operational routes (model load/unload, settings, keys, logs, diagnostics) |
|---|---|---|
| Token set | need the token | need the token |
| No token and no stored API keys | open | denied |
| `YUNSHU_AUTH_DISABLED=1` | open | open |

<Callout type="warn">
The token is an admin credential. `YUNSHU_AUTH_DISABLED=1` opens everything and is for local development only. `YUNSHU_HOST` defaults to `127.0.0.1`; set a token before binding `0.0.0.0`.
</Callout>

## API keys with quotas

Besides the static token, the operator can create several keys. Each key has scopes (`infer`, `admin`), an optional expiry and quotas (`requests_per_day`, `tokens_per_day`, `max_concurrent`). Manage them on the console Keys page or through the API with admin scope.

<Steps>
<Step>

Create a key. The response carries `secret` once; only a hash is stored in `~/.yunshu/keys.json` (mode 0600).

```bash
curl -s -X POST localhost:8000/v1/yunshu/keys \
  -H "Authorization: Bearer $YUNSHU_AUTH_TOKEN" \
  -H 'content-type: application/json' \
  -d '{"name":"laptop","scopes":["infer"],"quotas":{"requests_per_day":1000,"max_concurrent":2}}'
```

</Step>
<Step>

Give the secret to the client as its API key.

</Step>
<Step>

Watch per-key daily usage (requests, prompt, completion and cached tokens, errors):

```bash
curl -s localhost:8000/v1/yunshu/usage -H "Authorization: Bearer $YUNSHU_AUTH_TOKEN"
```

</Step>
</Steps>

`PATCH` and `DELETE` on a key edit and remove it, and `POST /v1/yunshu/keys/{id}/rotate` re-issues it. Over a quota the answer is `429` in the route's own error dialect with `Retry-After`. The routes are listed in [Yunshu extensions](/docs/api/extensions) and [Operations](/docs/api/operations).

Keys are not tenants. Authenticated clients share Files, stored completions and Evals data; there is no per-key isolation or RBAC. The Realtime WebSocket accepts keys but does not count quotas.

## Write settings

`GET /v1/yunshu/config` lists every setting with its value, default, source and when a change applies (`live`, `reload` or `restart`). `PATCH /v1/yunshu/config` validates and persists changes atomically (all or nothing, file mode 0600). An environment or CLI value still wins and is reported as `overridden`. `dry_run` previews a change.

Settings that need a restart are flagged so the console prompts you. `POST /v1/yunshu/service/restart` restarts the server only when it runs under launchd. The console Settings page does the same with a search box and per-setting controls. All settings are described in [Configuration](/docs/guides/configuration).

## CORS

`GET` and `PATCH /v1/yunshu/cors`, and the console Settings page, edit the allowed origins live. The default `YUNSHU_CORS_ORIGINS` is `http://localhost:3000,http://localhost:8000`.

- Origins are `scheme://host[:port]`, at most 50.
- A wildcard (`*`) needs an explicit confirmation, is never combined with other origins, and disables credentials. Browsers that send cookies or authorization headers must use explicit origins.
- The same list is checked against the `Origin` header of the Realtime and text WebSockets.
- Bind address and LAN exposure are read-only through this API.

## Host and Origin checks

A server bound to a loopback address checks the `Host` header, so a web page cannot reach it through DNS rebinding. Accepted: `localhost` (also `localhost.` and `*.localhost`), any `127.0.0.0/8` form (`127.0.0.1`, `127.1`), `[::1]`, and the unspecified address (`0.0.0.0`, `[::]`), with any port. Anything else gets `403` naming the header value and the setting. A server bound to `0.0.0.0` checks nothing unless `YUNSHU_ALLOWED_HOSTS` is set.

- A reverse proxy, `tailscale serve`, a cloudflared tunnel or `ssh -L` that forwards a public name as `Host` to a loopback server needs that name in `YUNSHU_ALLOWED_HOSTS` (comma-separated; `*` turns the check off).
- `host.docker.internal` is not accepted on a loopback bind: a container reaches the host's loopback only if the server listens beyond it (`YUNSHU_HOST=0.0.0.0`), and then the check is off anyway.
- A state-changing request with an `Origin` header and no credentials must come from loopback, the request's own origin, or `YUNSHU_CORS_ORIGINS`. For custom schemes list `scheme://*` (for example `vscode-webview://*`) or the exact origin (`app://.`). `Origin: null` is always refused. Requests that carry `Authorization` or `x-api-key` are exempt.

## Failed sign-ins

A non-loopback client address that presents a wrong credential 20 times within 60 seconds gets `429` with `Retry-After` for further wrong credentials. A correct token or key is always accepted and clears that client's count, and a request without any credential is answered `401` and not counted. When `YUNSHU_TRUSTED_PROXIES` lists the connecting proxy, the last `X-Forwarded-For` entry is the client address; otherwise the peer address is used.

## Other protections

- Authorization, API-key and cookie headers are dropped when a model download redirects to another origin.
- Realtime ephemeral secrets (`ek_...`) and credentials in log lines are redacted. Transcription secrets cannot create model responses.
- `web_fetch` blocks private, loopback and link-local addresses, also after redirects, unless `YUNSHU_WEB_FETCH_ALLOW_PRIVATE=1`. Repository IDs with path traversal are rejected before disk access.
- `YUNSHU_RATE_LIMIT_RPM` (default `0`, off) limits requests per client per minute; set it when the server is exposed to other machines.
- No usage analytics are sent. See [Host telemetry](/docs/guides/telemetry) for what is sampled locally.
