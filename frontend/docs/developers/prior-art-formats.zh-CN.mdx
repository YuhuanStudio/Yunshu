description: Yunshu 加载哪些已发布的 embedding、reranker 与分类器 checkpoint 格式、各自使用哪个 loader，以及如何对照上游实现检查这些 loader。

对于检索模型，Yunshu 直接加载实际发布的格式，而不要求私有转换。撰写 loader 之前，会先寻找既有的 MLX 移植、checkpoint 格式或运行环境，并加载该格式。本页列出涵盖的范围、刻意不支持的项目，以及一致性检查的做法。这是维护者参考；端点请见 [Embeddings](/docs/api/embeddings) 与 [Rerank](/docs/api/rerank)，衍生文件的来源请见[上游追踪](/docs/developers/upstream-tracking)。

## 它做什么

| 系列 | Loader | 备注 |
|---|---|---|
| EmbeddingGemma 2（bf16、affine 4-bit 与其他已发布的量化） | `python/yunshu_engine/embedding_gemma2_loader.py` 的 `load_published_model`：已安装 `mlx_vlm.models.embedding_gemma2` 时使用维护中的 `mlx_vlm.embedding_loader.load_embedding_model`（strict）；否则使用衍生 loader | 衍生的后备方案使用依 Hugging Face `embedding_gemma2` 架构撰写、vendored 的 MIT 文本塔，以及 mlx-vlm 的 Gemma 4 视觉与音频塔。量化模块依 checkpoint 的 scale 建构；视觉与音频塔可保留浮点权重；打包的整数张量绝不转成浮点。未量化的 checkpoint 沿用原本的浮点 loader。来源记录在 `vendor.json` |
| BERT、RoBERTa、XLM-RoBERTa 编码器与串行分类器 | mlx-vlm 维护中的 encoder loader 搭配 `SequenceClassificationModel` | 涵盖使用裸 backbone 名称的已发布 BGE 转换、单标签与多标签 head，以及带浮点或量化 head 的量化编码层。缺少 backbone 或 head 张量会是加载错误 |
| Qwen3 yes/no reranker | 在 mlx-lm 量化 loader 上使用官方的 instruction、prefix 与 suffix 配方 | 与转换后 checkpoint 自带的 `query` 与 `document` 角色模板一致 |
| Qwen3-VL 检索 | 已安装的 `mlx-embeddings` `model.process` API | 没有任何 GPL 原代码被拷贝进 Yunshu |

空的 embedding 输入会回传空清单，加入默认 instruction 时不会修改调用端的输入字典。

## 为什么

用户会直接带来 Hugging Face 上发布的 checkpoint。若 loader 悄悄换成不同的 head 或模板，会回传看似合理但错误的矢量与分数，因此每种格式要不就和上游一样正确加载，要不就以可据以处理的错误失败。

## 保证

- checkpoint 缺少 head 或 backbone 时是加载错误，绝不悄悄替换。
- `JinaForRanking`（Jina v3）是另一种架构，仍不支持：它训练好的排序 head 不能用 Qwen 的 yes/no logits 取代。
- Qwen3 reranker 的模板很重要：已发布的 0.6B 4-bit chat 模板预期 `query` 与 `document` 角色。若服务改传 `user`，该模板会丢掉 query 与 document，使不同的配对产生相同的 token id 与 logits。Yunshu 使用与转换后角色模板相符的官方配方。

## 限制

- 2026-10-08 的 Hugging Face 盘点显示，Google EmbeddingGemma 2 与所检查的每个 mlx-community 转换版本都只有单一 `model.safetensors`，因此这些已发布快照不会触发多分片加载的缺陷。重新打包或私有的多分片 checkpoint 可能会遇到。这是有日期的盘点，不是对未来上传的承诺。
- 与 `mflux` 的扩散模型比较是稽核，不是服务路径。经查看的 `mflux` 对应会丢掉没有 `mflux` safetensors metadata 的 affine 4-bit diffusers checkpoint 的 scale 与 bias，所以探测先解码权重，并把结果标示为含格式桥接的浮点参考。它不是原生量化加载，也不改变任何服务默认。

## 如何验证

- CPU 单元测试：`tests/unit/test_prior_art_check.py`、`tests/unit/test_priorfix_capabilities.py`、`tests/unit/test_priorfix_probes.py` 与 `tests/unit/test_priorfix_mflux_reference.py`。
- `scripts/dev/yv ab --base <sha> --cand <sha> --suite embedding --label <name>` 会加载 bf16、4-bit，以及重新打包成两个分片的真实 bf16 checkpoint，在 Mac 上比较 Yunshu 的封装与直接调用上游模型的结果，并对 bf16 矢量套用 0.99985 的 fp32 cosine 下限。量化精度另外回报。
- `--suite priorart` 运行有界的检索、Omni 预处理输入与固定种子的扩散比较；`--env PRIORART_KINDS=capabilities` 在一次 GPU 准入内，以独立的子进程运行 Gemma 各格式、检索、分类器、扩散稽核与 Omni 预处理，每个项目保留一份证据档与回传码，并拒绝缺漏、过期或设备错误的证据。`PRIORART_KINDS=diffusion-timing` 以 256 px、2 步、种子 7 运行三组交错配对，并连同确切的工作负载回报中位数。

这些是针对特定模态的稽核，不纳入一般 LLM 套件。扩散比较的时间不决定性能或默认。以上全都使用 GPU 队列；见[验证](/docs/developers/verification)。
