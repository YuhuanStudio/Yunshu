title: Console
description: The web console the Yunshu server hosts for watching the engine, managing models and keys, reading logs, trying the API and reading these docs.
---

The console is a web application served by its own light process (`yunshu console`, port 8100), apart from the engine. That process serves the console and these docs, passes the console's API calls on to the engine, and records the history, so the console stays usable and keeps recording while the engine restarts or crashes. It is a view onto one engine: live status, requests, models, caches, logs, API keys, settings and this documentation. It does not own the engine process; service restart is available under launchd. It is not a chat product.

<Callout type="info">
The console speaks Traditional Chinese, Simplified Chinese and English. It follows your browser's language and the choice is kept in the browser; switch it from the language button in the top bar. This documentation follows the same choice.
</Callout>

## Open the console

Start the server as usual: `yunshu serve` starts the console process next to the engine. Open `/console/` on the console's port, `http://127.0.0.1:8100/console/` by default (the engine keeps 8000). `--no-console` skips it, `--console-port` moves it, and `yunshu console --engine http://host:8000` runs it alone, for example against an engine on another machine. `yunshu service install` runs it as its own launchd job, so it keeps serving and recording while the engine restarts. The old `http://127.0.0.1:8000/console/` still works for one release as a redirect to the console process.

The static pages are public so that you can enter a token in the browser. Every API call the console makes still follows the normal authentication rules. Reading status, history, requests, models and cache views needs no token on a default local server. Management pages (API keys, logs, service, CORS) need the admin token, and show a notice with a link to Settings when it is missing. Enter `YUNSHU_AUTH_TOKEN` or an admin key in Settings; by default it stays in page memory only and is cleared when you reload.

If `/console/` answers 404 with the text "Yunshu Console is not built", the installed package does not contain the console build. The API is not affected. A source checkout builds the console with Node.js 22.18 or newer and pnpm:

```bash
cd frontend
pnpm install --frozen-lockfile
pnpm build
```

The build is written to `python/yunshu_gateway/console_static`, which the console process serves.

## Pages

The sidebar has six sections: Overview, Requests, Diagnostics, Models, Playground and Settings. Logs is a Diagnostics tab; Downloads and Cache are Models tabs; Keys and API access are Settings tabs. Docs opens from the top bar. Existing tab addresses remain valid.

| Page | What it does |
|---|---|
| Overview | Live engine state: phase (queued, prefill, decode), throughput, memory, caches, active requests. Updates about four times a second while a request runs and calmly when idle. |
| Requests | Live and finished requests with phase timelines, token and cache details, filtering, CSV export and per-request cancel. |
| Logs | The server log ring with level and text filters and a live tail. |
| Diagnostics | Health checks, host readouts, a support-bundle preview and raw diagnostic data. |
| Models | Loaded and available models with memory figures; load, unload, warm up, fit checks and idle retention. |
| Downloads | Download models from Hugging Face with progress, disk-space check and cancel. |
| Cache | Prefix-cache tiers (memory, warm, SSD) with entries, lifecycle events and clear actions. |
| Playground | Streaming chat with generation settings, tools, images, token confidence and generated code snippets. |
| API access | Connection snippets for your server and a catalogue of the routes it registers. |
| Docs | These pages, searchable from the command palette. |
| Keys | Named API keys with scopes, expiry and rolling-day quotas, and per-key usage. |
| Settings | Server address and token, theme and language, every engine setting with its source, CORS and service restart. |

## History and what happens when the engine is down

The console process reads the engine once a second and keeps the history in `~/.yunshu/console-history.sqlite`: 1 s resolution for the last hour, 10 s for 24 hours, 1 minute for 30 days, plus the finished-request log (numbers only, never prompts or outputs). On open, the charts (15 minutes to 30 days) and the request list backfill from it, then the live feed continues. While the engine is unreachable nothing is recorded, so the span shows as a gap and an event ("engine unreachable", "engine reachable again", "engine restarted", "model failed to load"), never as a line drawn across it.

When the engine does not answer, the console says "engine offline since 18:02:11, retrying in 4 s" and keeps retrying (backing off to about ten seconds, and at once when you return to the tab or the network comes back). Pages that show engine data keep their last data, dimmed and marked stale; the docs and Settings are unaffected. If the engine is up but the model failed to load, the page shows the error and Load model stays usable. A page that fails does not take the console down.

## Status and the status band

The separate floating status pills at the bottom of a desktop page shows the engine state, the loaded model and memory. Click it (or the compact pill on a phone) to open the status island: live phase, throughput, memory by owner and the host. Values the server did not report are shown as unavailable, not as zero.

If a refresh fails the console keeps the last numbers and says so; when the engine cannot be reached it shows an offline banner with Retry and Connection settings.

## Command palette

Press `⌘K` (`Ctrl K` on other systems) to open the command palette. It jumps to pages, runs actions such as loading a model or clearing a cache, switches language, and searches these docs: type two or more characters and matching pages and sections appear under Docs. `?` lists the keyboard shortcuts.

## Connection settings

By default the console talks to the same origin that served it. In Settings you can point it at another Yunshu server; that server must then allow the console's origin through its CORS configuration (`YUNSHU_CORS_ORIGINS`, editable in Settings when you have the admin token). Only the server address, theme and language are saved in the browser; the token is saved only if you ask for it.

## Notifications

The bell in the top bar opens the notification center (Notifications). It lists what changed while the console was watching, newest first, at most 50; the badge counts unread items, and opening the panel marks them read. Clear all empties it. Each row links to the page that explains it.

| Event | Raised when | Leads to |
|---|---|---|
| Model loaded / Model failed to load | a model's loaded or error state changes between two status reads | Models |
| Download finished / Download failed | a download that was queued or running ends | Downloads |
| Engine unreachable / Engine back online | the engine stops or starts answering | Diagnostics / Overview |
| Engine restarted | the reported uptime goes backwards | Diagnostics |
| Memory pressure is high | Metal active memory reaches 80% of unified memory; clears 5 points lower | Models |
| Server errors are rising | 3 or more 5xx responses within a minute; at most once per 5 minutes | Requests |

Only warnings and errors also pop up as a toast; the rest wait in the center. The first reading after you open the page never raises anything, and downloads that had already finished are not announced.

<Callout type="info">
The events are derived in your browser from the status, request and download reads the console already makes. They are kept in `sessionStorage` per server address, so they survive a reload of the tab but not a new tab, and nothing is sent to the server. This is separate from the recorded history and its engine events, which the console process stores.
</Callout>

## Memory ledger

The ledger answers "who holds the unified memory". It is fed by `/v1/yunshu/memory` on the engine, which needs inference permission, and the console re-reads it every few seconds while the page is visible. It appears in three places:

- **Models**, in a model's detail, under Memory holders.
- **Status island**, under Metal memory (with Swap, Memory pressure and the Reserve pool).
- **Cache**, where the prefix-cache share is shown as "from the memory ledger".

The table (Owner, Size, Reclaimable) lists Model weights, Prefix cache (RAM), Prefix cache (warm tier), KV of active requests, Reserve pool and Other, drawn as one bar against Metal memory. Marks show the peak since the server started, the Metal recommended limit and the wired limit.

- A size the server has no counter for is shown as Unknown, not as 0; an estimate is labelled estimated.
- When the owners add up to more than active Metal memory, "Other" shows 0 and the overshoot is stated.
- An engine without the route shows "This engine version does not report memory owners"; polling then stops.

See [Memory](/docs/internals/memory) for how each owner is counted.

## Speculation and stage latency

Both panels live on the Requests page and read the engine's finished-request records (`/v1/yunshu/requests/recent`).

**Speculative decoding** sits under the request list. It says how many of the last finished requests reported speculation, then groups them by Mode with Requests, Acceptance (total accepted tokens divided by total drafted tokens, over requests that reported both), Accepted / drafted tokens and Rounds; copy-draft rounds are called out. Requests with no speculation record are counted as plain decode, and requests with a mode but no counters are left out of the rate. The engine reports only per-request totals, so there is no per-depth chart. A second block, Engine counters (Model, MTP cycles, Accepted, Rejected, Adaptive draft), is read from `/debug/spec-decode` and covers everything since the engine started; if `/debug` is off it says the engine does not provide them.

**Stage latency** is the request waterfall, shown in a request's detail. Stages are Model lease, Gateway admit, Engine queue, Template, tokenize, Prefix-cache restore, Prefill, First decode and First flush, with time zero at gateway receive.

<Callout type="warn">
A stage the engine did not observe is listed under "Not reported", never drawn as zero. Prefill end is a host callback boundary, not a GPU profile; template and tokenize include media preparation; First flush is the server finishing the send, not the client receiving it. Rows that the page assembled from status polls (no engine record) have no waterfall, and an older engine shows "does not report stage latency yet". If the engine has host telemetry, the detail also shows an energy estimate for the prefill and decode windows; it includes other processes and idle power.
</Callout>

## Realtime health

On Diagnostics, the Realtime connection card (Test connection) checks the path from this browser to the engine's Realtime WebSocket (`/v1/realtime`, over `ws` or `wss` to match the page). It opens the socket once and waits for the first event, then shows Connect, First event, Server latency and Buffer depth, each marked browser or server. It sends no audio and uses no GPU, so it proves reachability, not speech quality; a figure the engine does not report is left out rather than shown as 0. See the [Realtime API](/docs/api/realtime).

## Tools tester and image to text

Both open from the Playground toolbar and use the model selected there.

### Tools

Tools opens the tool-call and structured-output tester. On the Tool calls tab, paste tool definitions as JSON (checked as you type: a name of 1 to 64 letters, digits, underscores or hyphens, `parameters` as an object schema), enter a prompt and press Send first round. Each round shows whether the engine called a tool, and whether the arguments are valid JSON, name a tool you defined and follow the schema. Fill in a result and press Send results and continue for the next round, up to a round limit; Start over resets. On the Structured output tab, give a JSON schema and press Send: the reply is checked as JSON and against the schema. The page checks a subset of JSON Schema and lists the keywords it skipped, and the response does not say whether constrained decoding enforced the schema; only the result is checked. Requests go to `/v1/chat/completions`. See [Structured output](/docs/guides/structured-output).

### Image to text

Image to text (OCR dialog) takes a PNG, JPG, WEBP, TIFF or BMP up to 10 MB, sends it to `/v1/ocr` and shows the text read, with the model and token usage. The button is disabled with "No OCR or vision model is loaded" when no loaded model can answer; an OCR-type model is preferred, else the first loaded vision model. The image goes to the engine only and is not kept. The engine returns text only, so there are no boxes on the image and no confidence figure. See the [OCR API](/docs/api/ocr).

## Engine pinning, auto-discovery and measurement pause

These features belong to the console process (`yunshu console`), see [Console process](/docs/internals/console-process).

- **Auto-discovery.** `yunshu console --engine auto` (or `YUNSHU_CONSOLE_ENGINE=auto`) keeps one console open across engine restarts and port changes. Every `YUNSHU_CONSOLE_DISCOVER_S` seconds (2) it probes the candidate ports with `/health`; `YUNSHU_CONSOLE_DISCOVER_PORTS=all` (the default) takes every TCP port listening on this Mac, or give a list such as `8000,18990-18999`. Only a port that answers like a Yunshu engine counts. It stays on the engine it follows, and moves to the most recently started live engine after two missed probes.
- **Pinning.** The status island lists the live engines (Engines: port, model, uptime). Use pins one, and it wins while it is live; Follow the newest unpins. The same is available through the console process's engines route (`/console/api/engines`, also under `/v1/yunshu/console/engines`).
- **Waiting.** With no live engine the island says "Waiting for an engine" and the console connects as soon as one starts; a short outage is shown calmly as a restart rather than a fault.
- **Measurement pause.** While the file named by `YUNSHU_CONSOLE_PAUSE_FILE` holds `{"pause": true, "until": ..., "reason": "..."}`, the console polls and probes no engine, so a monitor cannot perturb a timing run, and the island shows "Paused for a measurement: reason". Requests you make yourself still go through. The pause ends at `until`, two hours after the file's last write when `until` is null, or when the file is removed.

<Callout type="info">
Request history records the engine URL and start time with each request, so a switch shows as a separate session, marked by an `engine_switched` event.
</Callout>

## Network and CORS

Settings has a Network and CORS tab; changing it needs the admin token.

- **Network** is read-only: the address the console uses, and Reachable from, either This machine only or Local network. It shows the `yunshu service install --force --host 127.0.0.1` or `--host 0.0.0.0` command to switch, because the listen address is changed by reinstalling the service. Before opening the local network, set `YUNSHU_AUTH_TOKEN` or create an API key, and allow only the origins you need.
- **CORS origins** edits which websites may call the server from a browser. Add an origin as `http://` or `https://` plus host, with no path, or a lone `*`; `*` cannot be mixed with other origins and needs an explicit confirmation, because it lets any website call the server (without credentials). The page says whether this console's own origin is allowed. Save applies immediately; Reset to default restores the default.
- If `YUNSHU_CORS_ORIGINS` or a command-line flag sets the list, that wins over the config file: the editor says so, and edits are saved but do not change the running value.

See [Authentication and keys](/docs/guides/auth-and-keys) for the full CORS rules.

## What the console does not do

- It is not a multi-user control plane: keys carry scopes and quotas for one local server, nothing more.
- It keeps no durable chat history; the playground library is stored in your browser only.
- Prompts and responses are never stored by the console's request views, only metadata.
