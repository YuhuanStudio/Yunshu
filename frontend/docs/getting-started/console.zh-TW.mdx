主控台是由它自己的輕量程序（`yunshu console`，連接埠 8100）提供的網頁應用，與引擎分開執行。這個程序提供主控台與這份文件、把主控台的 API 呼叫轉送給引擎，並記錄歷史，所以引擎重新啟動或當機時，主控台仍可使用、仍持續記錄。它是觀察單一引擎的視窗：即時狀態、請求、模型、快取、日誌、API 金鑰、設定與這份文件。它不負責啟動引擎，也不是聊天產品。

<Callout type="info">
主控台支援繁體中文、簡體中文與英文，預設跟隨瀏覽器語言，選擇會保存在瀏覽器；可從上方列的語言按鈕切換。這份文件也跟隨同一個選擇。
</Callout>

## 開啟主控台

照常啟動服務：`yunshu serve` 會在引擎旁邊啟動主控台程序。在瀏覽器開啟主控台連接埠的 `/console/`，預設是 `http://127.0.0.1:8100/console/`（引擎維持 8000）。`--no-console` 可略過、`--console-port` 可更換連接埠，`yunshu console --engine http://host:8000` 可單獨執行，例如監看另一台機器上的引擎。`yunshu service install` 會把它安裝成獨立的 launchd job，引擎重新啟動期間它仍持續服務與記錄。舊的 `http://127.0.0.1:8000/console/` 在一個版本內仍可使用，會導向主控台程序。

靜態頁面是公開的，這樣你才能在瀏覽器輸入權杖。主控台發出的每個 API 呼叫仍遵守一般驗證規則：預設的本機服務不需要權杖就能讀取狀態、歷史、請求、模型與快取檢視；管理頁面（API 金鑰、日誌、服務、CORS）需要管理員權杖，缺少時會顯示提示並連到設定。請在「設定」輸入 `YUNSHU_AUTH_TOKEN` 或管理員金鑰；預設只保存在頁面記憶體，重新整理後即清除。

若 `/console/` 回應 404 並顯示「Yunshu Console is not built」，表示已安裝的套件不含主控台建置，API 不受影響。從原始碼執行時，以 Node.js 22.18 以上與 pnpm 建置：

```bash
cd frontend
pnpm install --frozen-lockfile
pnpm build
```

建置結果寫入 `python/yunshu_gateway/console_static`，由主控台程序提供。

## 頁面

側邊欄有六區：總覽、請求、診斷、模型、推理測試與設定。日誌在診斷分頁；下載與快取在模型分頁；金鑰與 API 存取在設定分頁。文件從頂端列開啟，原有分頁網址仍有效。

| 頁面 | 功能 |
|---|---|
| 引擎總覽 | 即時引擎狀態：階段（排隊、預填、解碼）、吞吐量、記憶體、快取與進行中請求。請求執行時每秒更新約四次，閒置時放慢。 |
| 請求與效能 | 進行中與已結束的請求，含各階段時間軸、token 與快取細節、篩選、CSV 匯出與單筆取消。 |
| 日誌 | 伺服器日誌環，可依等級與文字篩選並即時追尾。 |
| 引擎診斷 | 健康檢查、主機讀數、支援包預覽與原始診斷資料。 |
| 模型庫 | 已載入與可用的模型及記憶體數字；載入、卸載、預熱、容量檢查與閒置保留。 |
| 下載 | 從 Hugging Face 下載模型，附進度、磁碟空間檢查與取消。 |
| 快取 | 前綴快取各層（記憶體、暖層、SSD）的項目、生命週期事件與清除操作。 |
| 推理測試 | 串流對話，含生成設定、工具、圖片、token 信心與產生程式碼片段。 |
| API 接入 | 你的服務連線片段，以及它註冊的路由目錄。 |
| 文件 | 這些頁面，可從命令面板搜尋。 |
| 金鑰 | 具名 API 金鑰：權限範圍、到期時間、滾動日配額與各金鑰用量。 |
| 設定 | 服務位址與權杖、主題與語言、每個引擎設定及其來源、CORS 與服務重新啟動。 |

## 歷史，以及引擎離線時

主控台程序每秒讀取一次引擎，把歷史保存在 `~/.yunshu/console-history.sqlite`：最近一小時 1 秒解析度、24 小時 10 秒、30 天 1 分鐘，另有已結束請求的紀錄（只有數字，從不保存提示詞或輸出）。開啟時，圖表（15 分鐘到 30 天）與請求列表會先從這裡回補，再接上即時資料。引擎連不上的期間不會記錄，所以那一段會顯示為缺口與事件（「引擎無法連線」「引擎恢復連線」「引擎重新啟動」「模型載入失敗」），絕不會畫一條線穿過去。

引擎沒有回應時，主控台會顯示「引擎自 18:02:11 離線，4 秒後重試」並持續重試（退避到約十秒，回到分頁或網路恢復時立即重試）。顯示引擎資料的頁面保留最後的資料，變暗並標示為過期；文件與設定不受影響。引擎在線但模型載入失敗時，頁面顯示錯誤，「載入模型」仍可使用。單一頁面出錯不會讓整個主控台當機。

## 狀態與狀態列

桌面頁面底部獨立的浮動狀態膠囊顯示引擎狀態、已載入模型與記憶體。點它（手機上是精簡膠囊）會展開狀態島：即時階段、吞吐量、各擁有者的記憶體與主機資訊。伺服器沒有回報的值顯示為無法取得，而不是 0。

更新失敗時，主控台保留上一次的數字並註明；連不上引擎時會顯示離線橫幅，附「重試」與「連線設定」。

## 命令面板

按 `⌘K`（其他系統為 `Ctrl K`）開啟命令面板：可跳到頁面、執行載入模型或清除快取等動作、切換語言，也能搜尋這份文件，輸入兩個字以上，符合的頁面與段落會列在「文件」之下。按 `?` 可看鍵盤快速鍵。

## 連線設定

預設情況下，主控台連到提供它的同一個來源。你可以在「設定」改指向另一台 Yunshu 服務；該服務必須透過 CORS 設定（`YUNSHU_CORS_ORIGINS`，有管理員權杖時可在設定頁編輯）允許主控台的來源。瀏覽器只保存服務位址、主題與語言；權杖只有在你要求時才保存。

## 通知

上方列的鈴鐺會開啟通知中心（通知）。它依時間由新到舊列出主控台在監看期間發生的變化，最多 50 筆；徽章顯示未讀數量，打開面板即標為已讀，「清除全部」會清空。每一列都連到能說明該事件的頁面。

| 事件 | 觸發時機 | 前往 |
|---|---|---|
| 模型已載入／模型載入失敗 | 兩次狀態讀取之間，模型的已載入或錯誤狀態改變 | 模型 |
| 下載完成／下載失敗 | 排隊中或進行中的下載結束 | 下載 |
| 引擎無法連線／引擎已恢復連線 | 引擎停止或恢復回應 | 診斷／總覽 |
| 引擎已重新啟動 | 回報的運作時間倒退 | 診斷 |
| 記憶體壓力偏高 | Metal 使用中記憶體達統一記憶體的 80%；回落 5 個百分點後解除 | 模型 |
| 伺服器錯誤增加 | 一分鐘內出現 3 個以上 5xx 回應；每 5 分鐘最多一次 | 請求 |

只有警告與錯誤會另外跳出提示訊息，其餘靜靜留在通知中心。開啟頁面後的第一次讀取不會產生任何通知，開啟前已完成的下載也不會被通知。

<Callout type="info">
這些事件是瀏覽器根據主控台本來就在讀的狀態、請求與下載資料推算出來的。它們依伺服器位址存放在 `sessionStorage`，重新整理分頁後仍在，但開新分頁就不會，也不會傳給伺服器。這與主控台程序記錄的歷史及其引擎事件是兩回事。
</Callout>

## 記憶體帳本

記憶體帳本回答「統一記憶體被誰佔用」。資料來自引擎的 `/v1/yunshu/memory`（需要推論權限），頁面可見時主控台每隔數秒重新讀取。它出現在三個地方：

- **模型**：某個模型的詳細資料中的「記憶體持有者」。
- **狀態島**：Metal 記憶體區塊（連同 Swap、記憶體壓力與保留池）。
- **快取**：前綴快取的佔用量會標示「來自記憶體帳本」。

表格（持有者、大小、可回收）列出模型權重、前綴快取（記憶體）、前綴快取（暖層）、進行中請求的 KV、記憶體保留池與其他，並以一條對照 Metal 記憶體的長條呈現。標記線顯示自伺服器啟動以來的峰值、Metal 建議上限與 wired 上限。

- 伺服器沒有計數器的大小會顯示「未知」，而不是 0；估算值會標示「估算」。
- 各持有者加總超過 Metal 使用中記憶體時，「其他」顯示 0，並說明超出的量。
- 沒有此路由的引擎會顯示「此引擎版本沒有提供記憶體持有者明細」，並停止輪詢。

各持有者如何計算，請見[記憶體管理](/docs/internals/memory)。

## 推測解碼與階段延遲

兩個面板都在「請求」頁，讀取引擎的已完成請求紀錄（`/v1/yunshu/requests/recent`）。

**推測解碼**位於請求列表下方。它先說明最近已完成的請求中有多少回報了推測解碼，再依「模式」分組，顯示請求數、接受率（已接受 token 總數除以草稿 token 總數，只計入兩個計數器都有回報的請求）、接受／草稿 token 與輪數；複製草稿（copy-draft）回合會另外標出。沒有推測解碼紀錄的請求視為一般解碼，有模式但沒有計數器的請求則不納入比率。引擎目前只回報每個請求的總數，所以沒有逐深度圖表。第二個區塊「引擎累計計數器」（模型、MTP 週期、接受、拒絕、自適應草稿）讀自 `/debug/spec-decode`，涵蓋引擎啟動以來的全部；若 `/debug` 關閉，會說明引擎未提供。

**階段延遲**是請求瀑布圖，顯示在單一請求的詳細資料中。階段有模型租用、閘道准入、引擎排隊、模板與分詞、前綴快取還原、預填、首個解碼與首次送出，時間零點是閘道收到請求的時刻。

<Callout type="warn">
引擎沒有觀測到的階段會列在「未回報」，絕不畫成 0。預填結束是主機端回呼的邊界，不是 GPU 剖析；模板與分詞包含媒體前處理；首次送出是伺服器送完資料，不代表用戶端已收到。由頁面根據狀態輪詢組出、沒有引擎紀錄的列沒有瀑布圖，較舊的引擎則會顯示「這個引擎還沒有提供階段延遲」。引擎有主機遙測時，詳細資料還會顯示預填與解碼區間的能耗估算，其中包含其他行程與閒置功耗。
</Callout>

## Realtime 連線健康

在「診斷」頁，「Realtime 連線」卡片（測試連線）檢查從這個瀏覽器到引擎 Realtime WebSocket（`/v1/realtime`，依頁面使用 `ws` 或 `wss`）的路徑。它只開啟一次連線並等待第一個事件，然後顯示建立連線、第一個事件、伺服器延遲與緩衝深度，並標明各項來自瀏覽器或伺服器。它不傳送音訊、不使用 GPU，所以證明的是連得到，而不是語音品質；引擎沒有回報的數值會省略，不會顯示成 0。請見 [Realtime API](/docs/api/realtime)。

## 工具測試與圖片辨識

兩者都從 Playground 工具列開啟，並使用該處選定的模型。

### 工具測試

「工具測試」開啟工具呼叫與結構化輸出測試。在「工具呼叫」分頁貼上 JSON 格式的工具定義（輸入時即時檢查：名稱為 1 到 64 個字母、數字、底線或連字號，`parameters` 為 object schema），輸入提示詞後按「送出第一輪」。每一輪都會顯示引擎是否呼叫了工具，以及引數是否為合法 JSON、是否指向你定義的工具、是否符合 schema。填入結果並按「送回結果並繼續」進入下一輪，直到輪數上限；「重新開始」會重置。在「結構化輸出」分頁提供 JSON schema 後送出，回覆會檢查是否為 JSON 並是否符合 schema。頁面只檢查 JSON Schema 的一個子集，並列出略過的關鍵字；回應也不會說明引擎是否用受限解碼強制執行 schema，這裡只檢查結果。請求會送到 `/v1/chat/completions`。請見[結構化輸出](/docs/guides/structured-output)。

### 圖片辨識

「圖片辨識」對話框接受 10 MB 以內的 PNG、JPG、WEBP、TIFF 或 BMP，送到 `/v1/ocr`，顯示辨識出的文字、模型與 token 用量。沒有任何已載入模型能回應時，按鈕停用並提示「沒有載入 OCR 或視覺模型，無法使用圖片辨識」；優先使用 OCR 類模型，否則用第一個已載入的視覺模型。圖片只送給引擎，不會被保留。引擎只回傳文字，所以不會在圖片上標出位置，也沒有信心數值。請見 [OCR API](/docs/api/ocr)。

## 引擎固定、自動探索與量測暫停

這些功能屬於主控台程序（`yunshu console`），請見[主控台程序](/docs/internals/console-process)。

- **自動探索。**`yunshu console --engine auto`（或 `YUNSHU_CONSOLE_ENGINE=auto`）讓同一個主控台在引擎重新啟動與換連接埠時保持開啟。每隔 `YUNSHU_CONSOLE_DISCOVER_S` 秒（預設 2）以 `/health` 探測候選連接埠；`YUNSHU_CONSOLE_DISCOVER_PORTS=all`（預設）會取這台 Mac 上所有正在監聽的 TCP 連接埠，也可以指定清單，例如 `8000,18990-18999`。只有回應方式像 Yunshu 引擎的連接埠才算數。它會留在目前跟隨的引擎上，連續兩次探測失敗後才改跟最近啟動的存活引擎。
- **固定。**狀態島會列出存活的引擎（引擎：連接埠、模型、運作時間）。「使用」會固定其中一個，只要它還活著就優先；「改為跟隨最新」則取消固定。也可透過主控台程序的 engines 路由操作（`/console/api/engines`，也可從 `/v1/yunshu/console/engines` 存取）。
- **等待。**沒有存活的引擎時，狀態島顯示「等待引擎啟動」，引擎一啟動主控台就會連上；短暫的中斷會以重新啟動的平靜樣式呈現，而不是當成故障。
- **量測暫停。**`YUNSHU_CONSOLE_PAUSE_FILE` 指定的檔案內容為 `{"pause": true, "until": ..., "reason": "..."}` 期間，主控台不輪詢也不探測任何引擎，監控就不會干擾計時實驗，狀態島會顯示「因量測暫停：原因」。你自己發出的請求仍會通過。暫停在 `until` 到期、`until` 為 null 時於檔案最後寫入兩小時後，或檔案被移除時結束。

<Callout type="info">
請求歷史會連同每個請求記下引擎 URL 與啟動時間，所以切換引擎會呈現為獨立的工作階段，並以 `engine_switched` 事件標示。
</Callout>

## 網路與 CORS

「設定」有一個「網路與 CORS」分頁，修改需要管理員權杖。

- **網路**是唯讀的：顯示主控台連線的位址，以及可連線範圍（僅本機或區域網路可連線）。它會顯示切換用的 `yunshu service install --force --host 127.0.0.1` 或 `--host 0.0.0.0` 指令，因為監聽位址要重新安裝服務才能變更。開放區域網路之前，請先設定 `YUNSHU_AUTH_TOKEN` 或建立 API 金鑰，並只允許你需要的來源。
- **CORS 來源**編輯哪些網站可以從瀏覽器呼叫這個伺服器。新增來源時寫成 `http://` 或 `https://` 加主機、不含路徑，或單獨一個 `*`；`*` 不能與其他來源並用，且需要明確確認，因為它會讓任何網站呼叫伺服器（不帶憑證）。頁面會說明這個主控台自己的來源是否被允許。儲存立即生效；「還原預設」會還原預設。
- 如果清單由 `YUNSHU_CORS_ORIGINS` 或命令列旗標設定，會優先於設定檔：編輯器會提示這點，編輯會被儲存，但不會改變正在執行的值。

完整的 CORS 規則請見[驗證、API 金鑰與 CORS](/docs/guides/auth-and-keys)。

## 主控台不做的事

- 它不是多使用者控制平面：金鑰的權限範圍與配額只針對這一台本機服務。
- 它不保存長期的對話歷史；推理測試的資料庫只存在你的瀏覽器。
- 請求檢視從不保存提示詞與回應，只有中繼資料。
